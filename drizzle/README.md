# Rybbit Postgres migrations

This folder holds committed SQL migrations generated by `drizzle-kit generate`
against the upstream Rybbit `schema.js` for the version pinned in
`../package/default.nix`.

At service start, `rybbit-postgres-migrate.service` runs `drizzle-kit migrate`
(wired up in `../module.nix`) which applies any unapplied migration files
non-interactively and records them in the `drizzle.__drizzle_migrations`
tracking table.

## Why not `drizzle-kit push`?

`push` diffs the live DB against `schema.js` and, when it cannot
unambiguously decide whether a column was added or renamed, prompts the
operator. Under systemd there is no TTY, so `push` silently bails, marks the
service as successful, and leaves the database in a partially migrated state.
This is exactly how Rybbit 2.5.0 broke on upgrade (apikey `userId` → `referenceId`
rename plus new `team` tables). `migrate` has no interactive prompts — it just
applies committed SQL.

## Upgrading Rybbit

After bumping `version`/`rev`/hashes in `../package/default.nix`:

```bash
# Build the new server package so its schema.js is in the store
nix build .#server
SCHEMA=$(readlink -f result)/lib/rybbit-server/dist/db/postgres/schema.js

# Generate a delta migration against the committed snapshot.
# `drizzle-kit generate` reads drizzle/meta/*_snapshot.json, compares it to
# the new schema.js, and emits a new numbered .sql file plus an updated
# snapshot + journal entry.
nix run .#generate-migration -- "$SCHEMA" short-description

# Review the generated SQL carefully — especially any DROP COLUMN or
# DROP TABLE statements. Then commit drizzle/ together with the version bump.
git add drizzle package/default.nix
git commit -m "chore: update to vX.Y.Z"
```

On the next deploy, `drizzle-kit migrate` will notice the new journal entry
and apply the delta inside a transaction. If anything fails, the transaction
rolls back and the service unit fails loudly (no more silent partial state).

## Bootstrapping an existing database

If you already have a Rybbit database that was created by `drizzle-kit push`
(i.e. has no `drizzle.__drizzle_migrations` table), you must seed the tracker
once before the first `migrate` run, otherwise migrate will try to re-apply
`0000_init.sql` against already-populated tables:

```sql
CREATE SCHEMA IF NOT EXISTS drizzle;
CREATE TABLE IF NOT EXISTS drizzle.__drizzle_migrations (
  id SERIAL PRIMARY KEY,
  hash text NOT NULL,
  created_at bigint
);
-- `created_at` must be >= the `when` of the latest journal entry in
-- drizzle/meta/_journal.json. Using a far-future value is safe and makes
-- migrate skip everything already present.
INSERT INTO drizzle.__drizzle_migrations (hash, created_at)
VALUES ('bootstrap', 9999999999999);
```
